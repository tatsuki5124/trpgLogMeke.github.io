## ADR-001: 場面タイトルの強調手段

**Status:** Accepted

### Context

`h3.log-scene` の上余白は `margin-block-start: 2rem`。キャラクター発言（`1.7rem`）との差は約 `0.3rem`（≒5px）で、スクロール中に視認できる差ではない。「あの場面はどこ？」の再読時に場面転換点を素早く見つけられない問題がある。背景色はすでに4意味（タブ=グレー、情報=白、成功=水色、失敗=赤）に使用済みで第5の背景色は使えない。

`h3` 要素自体が見出し要素として既にセマンティックな重みを持っており、「h3 で十分目立っているか」は実際のサンプルを見て判断する。

### 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A: 現状維持 | `margin-block-start: 2rem`（現状） | h3要素のウェイトで十分とする場合 |
| B: 余白拡大のみ | `2rem → 3rem` | 白空間は増えるが「視線の錨」がない |
| C: `border-block-start` + 余白拡大 | 論理プロパティで区切り線を追加 | — |
| D: `::before` 水平線 | 全幅の水平線 | 縦書き時に物理的な向きが変わり崩れるリスクが最大 |

### Decision（サンプル確認後に確定）

**C案（`border-block-start` + 余白拡大）を採用する。**

`border-block-start` は CSS 論理プロパティのため、横書き・縦書きで同一ルールが書字方向に応じた位置に適用される。条件分岐なしに両モードで意味が一貫する。

- 横書き: `border-block-start` = 上端（場面タイトルの直上に区切り線）
- 縦書き（vertical-rl）: `border-block-start` = 右端（ブロック開始方向の前端）

意味・意図は両モードで一貫: 「このセクションが始まる前の区切りマーカー」。

```css
.log-scene {
  margin: 3rem 0 .65rem .5rem;
  padding-block-start: 0.75rem;
  border-block-start: 1px solid color-mix(in srgb, var(--log-speaker-color) 25%, transparent);
  color: var(--log-speaker-color);
}
```

比較出力に適用済み（`pnpm logmake:compare-output` で再生成）。

### Consequences

- スクロール中の場面境界が線で知覚できるようになる
- 背景色の視覚文法（4意味）を崩さない
- `border-block-start` の論理プロパティにより、縦書き時の条件分岐が不要（ADR-006と異なり無効化しない）
- 場面直前の地の文 `margin-block-end: 0.65rem` と合算すると `3.65rem` になる（地の文→場面タイトル間が広くなる）

### 残課題

- サンプルを見てA（現状）で十分かCが必要かを確定する
- `border-block-start` の色・opacity 最終値（候補: `rgba(136,136,136,0.25)`、ただし `--log-speaker-color` に合わせるか固定値かも検討）
- `margin-block-start: 3rem` でシーン頻度が高いセッションログを実際に確認する

## ADR-002: 地の文・KP/GM の扱い

**Status:** Proposed

### Context

CCFOLIA データ上、KP/GM/話者なしは他のキャラクターと構造的に同一（名前・色・テキスト）。しかし KP の発言は「状況提示・演出」であり PC の「行動宣言」とは情報の性質が異なる。現行比較案の narration スタイル（名前を非表示）は「最優先は会話追跡性」という前提と矛盾している。

### 検討した選択肢

| 案 | 内容 | 却下理由 |
|---|---|---|
| A: 通常話者扱い | 名前あり・speaker スタイル | 演出と行動宣言の区別がつかず場面転換が埋もれる |
| B: 名前なし narration | 名前を消して地の文として表示 | 会話追跡性を壊す。「最優先」前提と矛盾 |
| C: scene-named | 名前を残しつつ低 opacity + narrationColor | — |

### Decision

**C案（`scene-named`）を採用する。**

- `CharacterStyle` 型に `'scene-named'` を追加
- `buildOutputModel` での自動検出: 完全一致リスト `['KP', 'GM', '']`（話者なし）のみ。部分一致は実装しない
- 描画: 名前を `opacity: 0.55`・本文を `narrationColor`（`#555555` / ダーク `#b8b8b8`）で表示。名前は DOM に残すため会話追跡性を保つ
- `CharacterConfig.style` ドロップダウンに `scene-named` と `character`（通常話者）を両方出す

### Consequences

- 「会話追跡性」と「演出の視覚的区別」が両立できる（B案と違い名前を削除しない）
- 自動検出の完全一致リストは誤判定リスクが最小
- 「KP という名の PC」は `CharacterConfig.style` で `character` に戻せる
- ダークモードで narrationColor `#b8b8b8` + opacity `0.55` の組み合わせが WCAG AA（4.5:1）を満たすか要確認

### 残課題

- `scene-named` と現行の `scene` バリアントの関係整理（統合するか、`scene` を deprecated にするか）
- `renderSpeaker` に `scene-named` 分岐を追加する実装
- ダークモードでのコントラスト比検証（narrationColor × opacity × ダーク背景）

## ADR-003: 情報タブの扱い

**Status:** 要再検討（前提の見直し後）

### Context

CCFOLIA の「情報」タブはピン留め（メモ帳）として使うユーザーもいるが、情報タブにしか記載しないケースも大いにある。前者のみを前提とした「補助タブ同等化」は実態に合わない。情報タブの用途は以下のように多様:

1. **専用情報置き場**: 戦闘中の重要NPC情報、マップ情報など。メインタブには流さない
2. **ピン留め（メモ帳）**: メインタブと重複して同じ内容を情報タブにも投稿する運用

また、情報ブロック（技能ロール・アイテム獲得等の構造化データ）の扱いも情報タブ設計と連動する問題として存在する:
- 情報ブロックが補助タブ（グレー背景）内に入ると、白背景の情報ブロックが「浮いて見える」副作用がある

### 検討した選択肢

| 案 | 内容 | 問題 |
|---|---|---|
| 現状維持（メイン同等） | 変更なし | 重複コンテンツの問題は残る |
| A: 重複省略 | 一致エントリを自動検出 | 誤判定リスク・実装複雑 |
| B: 表示オプション化 | visible トグルをユーザーが選択 | 用途が多様なため「デフォルトどうするか」が難しい |
| C: 補助タブ同等化 | `isPrimaryTab` から外す | 情報タブを専用置き場として使うユーザーに情報ブロックの「浮き」問題が発生 |

### Decision

**前提の整理が先。現時点では情報タブの扱いを変更しない。以下を確認・整理した後に再決定する:**

1. **情報タブの用途実態の整理**: ピン留め運用 vs 専用情報置き場、どちらが主要ユースケースか
2. **情報ブロックの「浮き」問題**: 補助タブ内での `white` 背景情報ブロックの扱いを先に設計する
3. **情報ブロックの意味論的位置づけ**: 情報ブロックは「タブに属する情報」か「特定の会話に紐づく情報」か

### Consequences

- 情報タブの変更を急がないことで、情報ブロック設計と一体で考えられる
- 重複コンテンツの問題は引き続き残る（許容する）

### 残課題

- 情報タブの主要ユースケースを整理し、設計判断の前提を固める
- 情報ブロックが補助タブ内で「浮く」問題の解消案を検討（透明背景化 vs 別スタイル）
- 情報タブとメインタブで情報ブロックのスタイルを統一するか分けるかの方針

## ADR-004: HTML 構造刷新の適用タイミング

**Status:** Accepted

### Context

production は `.box5` / `.char` / `.KP` / `.bbb` などの旧 Vue 版クラス名をそのまま引き継いでいた。比較案は `log-section` / `log-entry--speaker` など BEM 的な意味論的クラス体系に刷新済み。4種の構造変更候補（`strong` 化・`aside` 化・`aria-label` 修正・`h4`→`p+strong`）がある。

### Decision

**影響範囲で仕分けし、段階的に適用する。**

**優先度1（副作用なし・即時適用）:**
- `title="雑談"` → `aria-label="雑談"` — CSS/JS の動作に影響なし
- `<h4 class="log-info-title">` → `<p><strong>` — 情報ブロック内のみ

**優先度2（スタイル調整を伴うが独立）:**
- `<span class="log-speaker">` → `<strong>` — `b`/`.char b` のスタイルを `strong` に読み替え

**優先度3（セクション構造変更）:**
- 補助タブ `<section>` → `<aside>` — `aria-labelledby`/`aria-label` との整合確認が必要

**優先度4（クラス名体系・進めてよい）:**
- クラス名体系の刷新（`.char` → BEM 体系）— 視覚仕様の確定を待たずに進める。ただし後方互換は保証しない旨を明示する

### Consequences

- `aria-label` と `h4` の修正は比較案の視覚仕様議論と切り離して進められる
- クラス名刷新は視覚仕様との結合度が高いため、先行させると後から修正が発生するリスクが高い
- ユーザーが保存済みの旧出力 HTML に独自 CSS を当てている場合、クラス名刷新時に後方互換は保証しない旨を明示する必要がある

### 残課題

- `aside` 化の際、CSS の `.tab` セレクタが `aside.tab` として機能するか確認
- `strong` 化に伴い `b { display: block; }` スタイルを `strong` に移す（`buildStyle` 内の対応）
- `<main class="log-frame">` への変更（現行 `<div class="box5">`）のタイミングをクラス名刷新と合わせて明示

## ADR-005: ログ全体の枠線

**Status:** Proposed

### Context

`.log-frame` の `border: double 5px frameColor` は「配布物らしさ」を出す意図。しかし `frameColor` とほぼ同系色の設定では二重枠がほとんど視認されない。タブ左ボーダー・情報枠・名前下線と合わせると「4層目の装飾」になる。ユーザーが `frameColor` を自由に設定する構造上、常に視認されることを保証できない。

### 検討した選択肢

| 案 | 内容 | 却下理由 |
|---|---|---|
| 廃止 | `border: none` | — |
| 維持（`solid` に変更） | `double` → `solid` + 濃い派生色 | ユーザー設定が白系や淡色のときにコントラストが取れない問題は根本解決しない |

### Decision

**廃止（`border: none` または記述削除）する。**

`margin: 6rem 2rem 2rem` によって frameColor の背景が `log-frame` の四辺に自然な「額縁」として残るため、枠線なしでも視覚的まとまりは成立する。

### Consequences

- 機能していないデコレーションが削除され、CSS の意図が明確になる
- モバイルでの「壁紙の上の白板」表示の見た目をダークモードを含めて実機確認する必要がある

### 残課題

- 廃止後のモバイル表示（特にダークモード、`log-frame` と frameColor 背景のコントラスト）の実機確認
- 比較 HTML で `solid` 派生色案を一度確認してから最終判断する価値はある（根拠を残す意味で）

## ADR-006: 発言境界（名前下線）の縦書き対応

**Status:** Proposed

### Context

確定事項として名前下線（`::after` で `border-block-end: 2px solid var(--log-speaker-color)`）を採用。`border-block-end` は縦書きで `inline-end` 方向（文字の右側）に変わる。横書きの下線は「発言者のラベル」として慣習的に読める文脈があるが、縦書きでキャラクター名の右側に細線が走る表示慣習はほぼ存在しない。

### 検討した選択肢

| 案 | 内容 |
|---|---|
| A: `border-inline-end` に切り替え | 縦書き専用スタイルで名前右側に線を表示 |
| B: 縦書き時は無効化 | `border-block-end: none` を縦書き分岐に追加 |

### Decision

**B案（縦書き時に名前下線を無効化）を採用する。**

```css
/* 縦書き分岐内 */
.char > b::after,
.log-speaker::after {
  border-block-end: none;
}
```

機能しない装飾は入れない。会話追跡性という最優先目標に対して、意味論的整合性の確認が難しい切り替え案よりリスクが低い。

### Consequences

- 縦書き時の名前境界マーカーがなくなる（別の区別手段で補完するかどうかは別途決定が必要）
- `::after` のセレクタが将来の HTML 構造刷新（`.char > b` → `.log-speaker`）と連動して変わる

### 残課題

- 縦書き時に発言境界を別の手段（余白・色差）で補完するかどうかの意思決定
- セレクタが production 現行クラス体系から将来体系に移行するタイミングとの整合

## ADR-007: ダーク時成功/失敗ハイライトの opacity と設計

**Status:** Accepted

### Context

ライトは `#7fbfff`（成功）/ `#ff7f7f`（失敗）を維持。ダークは `rgba(...)` で半透明にしており、現在 `0.56`（成功）/ `0.58`（失敗）。production では文字列置換でダーク用 gradient を生成しており、`buildOutputHtml` 内でライト/ダーク/縦書きの分岐が混在している。

### Decision

**opacity は現状（`0.56` / `0.58`）を暫定維持。設計を先に整理する。**

ハイライト色計算を `buildOutputHtml` から分離し、純粋関数 `computeHighlights(settings)` として切り出す。`defaults.ts` 側で一元管理することで、ダーク×縦書きの組み合わせが増えても条件分岐の爆発を防ぐ。

```typescript
// 現状（buildOutputHtml 内に散在）
const successHL = isVertical ? '...' : SUCCESS_HIGHLIGHT

// 推奨（純粋関数に切り出し）
const { successHL, failureHL } = computeHighlights({ isDark, isVertical })
```

opacity の最終値は比較 HTML を実機確認してから変更する。

### Consequences

- ライト/ダーク/縦書きの組み合わせが `computeHighlights` 一箇所で管理される
- opacity 変更が 1 箇所の修正で済むようになる
- ダーク×縦書きで gradient の向きが `to right` のままでよいかも同時に確認できる

### 残課題

- `computeHighlights` の切り出しを行うか、`buildStyle` への引数化にとどめるかの実装方針
- 比較 HTML でダークモード表示を確認してから opacity 最終値を決定
- ダーク×縦書きで gradient の向きを `to bottom` にすべきかの確認

## ADR-008: 本文色の設定化

**Status:** Proposed

### Context

「本文色はキャラクターカラーなし（標準色）」は確定済み。将来的に `標準色 / キャラクター色` を設定可能にするかどうかが未決。CCFOLIA のキャラクター色の多くは明るい背景向けの色であり、ダーク背景（`#2d2d2d`）に置いた場合に WCAG AA 基準（4.5:1）を割るケースがある。

### Decision

**現時点では設定化しない。型・UI ともに追加しない。**

設定化するなら WCAG AA 基準を担保する仕組み（色の自動補正、または警告 UI）とセットで設計する必要があり、現段階ではオーバーエンジニアリングになる。

将来設計の骨格として合意しておく内容:
- 設定名: `bodyTextColor: 'standard' | 'character'`
- デフォルト: `'standard'`
- ダーク時に `'character'` を選択した場合は本文色を適用しない（名前色のみ適用）か警告を出す

### Consequences

- 他の優先度の高い未決事項（場面タイトル・HTML 構造・情報タブ）の進行が妨げられない
- 将来設計の骨格は議論ドキュメントに記録しておくため再設計コストが最小

### 残課題

- 設定化の議論を再開するトリガー条件を明示（例: 「ダークモードのコントラスト自動補正の実装方針が決まったら」）
- 設定化した場合に `renderSpeaker` の `style="color: ${entry.color};"` を `<b>` タグのみに移動する変更が必要になる点を設計メモとして残す

## ADR-009: KP/GM を名前あり表示に戻せる UI

**Status:** Proposed

### Context

ADR-002 で `scene-named` を採用した場合、自動検出で `scene-named` になったキャラクターを `speaker` スタイルに戻すための UI が必要かどうかが未決。

### Decision

**既存の `CharacterConfig` 設定 UI に「自動検出マーク」を付加するにとどめる。KP/GM 専用 UI は作らない。**

- キャラクター設定リストで、自動検出によって `scene-named` にセットされたエントリに `（自動）` ラベルを表示
- スタイルのドロップダウンは `character` / `scene-named` / `item` を選択肢に持ち、変更はここで行う
- `CharacterStyle` 型から `scene` を除外しない（現行コードとの互換を維持）

### Consequences

- 専用コンポーネントを追加せず、`useLogmakePageState` の自動検出ロジックにフラグを持たせるだけで実現できる
- 「戻し操作」が既存の設定 UI 経路に一本化され、UI の複雑度が増えない

### 残課題

- `CharacterStyle` 型に `scene-named` を追加するタイミング（`buildOutputModel.ts` の自動検出実装と同時か、型定義を先行させるか）
- `scene` バリアント（現行コードに存在）を `scene-named` と統合するか、別物として残すかの最終判断
